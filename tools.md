## Two tools from the Atomic talk

### smolvm

[smolvm](https://github.com/smol-machines/smolvm) is an open-source (Apache-2.0) runtime for small virtual machines, built for sandboxing agents. Each workload gets its own hardware-isolated VM and kernel, booting from ordinary OCI container images without a Docker daemon. It came up in the Atomic talk: Outposts, Atomic’s commercial product in progress, will create a microVM per change and per review using smolvm.

- **Platforms:** Apple Silicon Macs (Hypervisor.framework), Linux with KVM, and Windows with the Windows Hypervisor Platform. The VMM is libkrun.
- **Network off by default.** Allow specific hosts, patterns or CIDRs, changeable on a running machine. Credentials can be substituted with placeholders so the workload never reads the real secret.
- **Branchable.** Checkpoint RAM, CPU state and disk; branch copy-on-write children of a live machine; rewind. A machine packs into one file or an OCI image.
- **SDKs** for TypeScript, Python, Rust and Go run in-process, locally or against the hosted smol cloud.

Why it matters: the Opening keynote (Mad Labs) argued that boundaries must come from isolation, not instructions. A per-task microVM with network off and placeholder credentials is that boundary for agents running untrusted code or parallel tasks. Compare it with [Claude Code’s built-in sandboxing](https://www.anthropic.com/engineering/claude-code-sandboxing) before adding a tool; smolvm’s edge is a full VM per task and branching. Start with the [security model](https://github.com/smol-machines/smolvm/blob/main/docs/security-model.md) and [limitations](https://github.com/smol-machines/smolvm/blob/main/docs/limitations.md) pages.

    brew install smol-machines/tap/smolvm   # macOS
    smolvm --help                           # agents can discover commands this way

### Markdown generic directives

Generic directives are a [long-running CommonMark proposal](https://talk.commonmark.org/t/generic-directives-plugins-syntax/444) for one syntax that extends Markdown with named, structured blocks. There are three forms: inline `:name[text]{attrs}`, leaf `::name[text]{attrs}`, and container `:::name` … `:::`. It is not part of the CommonMark spec, but the unified ecosystem implements it in [remark-directive](https://github.com/remarkjs/remark-directive), which parses directives into the syntax tree and leaves rendering to you.

Atomic’s intent files are Markdown with directives. In the demo, an acceptance-criterion directive carried an ID, a status, `verifiedBy` and evidence attributes, and a task directive pointed at the criterion it satisfied. Lee Faus recommended directives to anyone building a software factory. An illustrative example of the syntax (not Atomic’s exact schema):

    :::intent{id="INT-142" owner="orders-api"}
    ## Why
    Support staff can't see why an order was routed to manual review.
    ​
    ::criterion[The order detail API returns the routing rule ID and reason]{id="AC-1" status="met" verifiedBy="contract-tests" evidence="ci-run-4812"}
    ​
    ::task[Add the routing reason to the order detail response]{id="T-1" status="done" criteria="AC-1"}
    :::

Why it matters: it is a cheap way to make intents and evidence machine-checkable without leaving Markdown or Git, which is the part of Atomic’s workflow a team can adopt today. A pull request check could parse the criteria and require evidence for each.
